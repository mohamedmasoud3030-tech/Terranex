# ADR 0005 — S3 Real Estate operational slice

**Status:** Accepted for GF-005
**Date:** 2026-08-11

## Context

S3 must prove the first sector path from a Real Estate project to an economic property asset, cadastral parcel, acquisition/control evidence, development phase and milestone, operational history, and exact cost drilldown. S0–S2 already own project identity, parties, exact money, supplier obligations, payments, balanced journal postings, reversal, membership authorization, and audit. S3 must extend those facts rather than create a property ledger or infer accounting policy from the asset type.

## Decision

- `RealEstateProjectProfile` is one immutable sector profile per existing Real Estate `InvestmentProject`, containing only strategy and optional jurisdiction. A project can have multiple `PropertyAsset` roots. `Parcel` remains a subordinate cadastral/physical identity with decimal quantity plus one explicit unit (`M2`, `HECTARE`, or `FEDDAN`); no GIS subsystem is introduced.
- Property operational state is derived from append-only `property_asset_state_history`, not an editable asset status. The implemented lifecycle is exactly `CANDIDATE → DUE_DILIGENCE → ACQUIRING → HELD → DEVELOPING → HELD`. Database triggers lock the property root, validate the expected current state and transition edge, and record actor, time, reason, and material evidence reference. Each transition also references its immutable predecessor history row under a unique constraint, so two concurrent commands cannot both consume the same state even when they began with the same statement snapshot.
- The S3 control policy requires a recorded acquisition contract plus a successful, current acquisition check to enter `ACQUIRING`. Entering `HELD` requires the acquisition contract and separate effective, successful `TITLE` and `POSSESSION` records. Payment is deliberately not a control condition. Title, possession, and acquisition payment status are separate read-model fields, so a payment cannot mark an asset controlled and an unpaid/unlinked contract can still be controlled when the implemented legal/control evidence is present.
- Acquisition is an immutable operational/legal fact linked to the existing seller `Party`. Consideration and closing costs use the shared bigint/ISO-money boundary. An optional consideration obligation can reference an existing S2 obligation only when tenant, project, seller, amount, and currency match. Acquisition records never create payments or journals.
- Typed immutable control records cover only `ACQUISITION_CHECK`, `TITLE`, `POSSESSION`, `PERMIT`, and `INSPECTION`. Each records status, dates where relevant, responsible active member, result/notes, and an evidence reference. S3 uses metadata-only evidence references: the workflow can identify and audit the contract/report/register reference without requiring file upload or retrieval. Private Storage and versioned file metadata remain deferred until a real file workflow requires them; no generic folder DMS is scaffolded.
- Development phases are property-scoped with optional parcel scope, sequence, and planned dates. Phase state is derived from append-only history (`PLANNED → ACTIVE → COMPLETED | CANCELLED`). Milestones belong to one phase and use the same bounded state vocabulary. Actual start/completion times are derived from transitions. No task, Gantt, workforce, contractor, procurement, BOQ, or change-order model is introduced.
- Confirmed Real Estate events are immutable facts with occurred and recorded times, normalized optional property/parcel/phase/milestone references, responsible member, location, notes, optional evidence, and an optional quantity that is valid only with an explicit unit. This is direct fact capture, not event-sourcing infrastructure. The product remains online-first; no PWA/offline synchronization is introduced without field evidence.
- Property budgets use immutable line sets under numbered `PROPOSED` / explicitly `APPROVED` versions. A later approval does not overwrite prior approved history; reporting uses the latest approved version for the property. Budget approval is OWNER-only under the existing S2 OWNER/MEMBER boundary.
- `PropertyCostItem` is an immutable normalized dimension record pointing to exactly one existing S2 `cost_obligation`, a property, optional parcel/phase, cost category, and the operator/accountant's policy reference. It has no money or balance column. Composite tenant/project/property foreign keys and triggers reject cross-organization, cross-project, wrong-property parcel, and wrong-property phase combinations. Milestone costing is omitted because this slice has no genuine requirement for it.
- Committed cost is the outstanding portion of an S2 authorized obligation with an active authorization posting and active payments. Actual/cost-to-date is the exact debit-minus-credit total on S2 `PROJECT_EXPENSE` / `DEVELOPMENT_WIP` journal lines, including linked reversal effects. Budget variance is latest approved budget minus actual. Committed and actual are displayed separately and not added, because S2 recognizes the cost when authorizing the obligation and the open payable may overlap actual. Every amount drills to the dimension record, S2 obligation, and originating authorization batch.
- Management valuation is property-scoped and immutable except for the controlled `PROPOSED → APPROVED` review transition. It stores date, source, method, exact money, assumptions, confidence, evidence, preparer, and reviewer. Proposal and approval functions contain no journal command; audit explicitly records `accounting_effect: NONE`. It is labeled management valuation and is not cash, revenue, realized result, or an automatic IAS 2/16/40 or IFRS 13 treatment.
- Any active member may prepare sector baseline facts, controls, phases/milestones, events, budget proposals, and valuation proposals. OWNER confirms material property lifecycle, acquisition contracts, approved budgets, approved valuations, and retroactive classification of already-authorized S2 obligations. This reuses S2 authorization rather than creating a role catalogue or generic approval engine. All writes use authenticated, locked-search-path RPCs; material commands are payload-bound idempotent and audited. Browser roles receive RLS-filtered SELECT only and no table DML.

## Consequences

- S3 supplies an Arabic/RTL project Operations workspace with persistent project context, mobile reflow at 360px, honest loading/error/forbidden/empty states, separate title/possession/payment facts, state history, cost sources, and valuation labeling.
- Accounting classification remains the explicit S2 `EXPENSE` / `CAPITALIZABLE_WIP` choice and its policy reference. S3 does not claim IFRS compliance or infer inventory, PPE, or investment-property treatment.
- Sale/disposition, revenue/collection, derecognition, realized result, allocations/distributions, period close, leasing/property management, full construction ERP, documents/storage, and offline synchronization remain later slices.
