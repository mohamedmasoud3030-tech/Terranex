## تفصيل كل اختبار

### 1 و 2 — القراءة تعمل بالكامل
```
GET /rest/v1/transactions?select=id&limit=1        → HTTP 200  []
GET /rest/v1/financial_audit_logs?select=*&limit=1 → HTTP 200  []
```
`200` مع مصفوفة صالحة = المفتاح مقبول والصلاحيات ممنوحة. لو كان مُبطَلاً لكان الرد `401 Invalid API key`.

### 3 — 🔴 الدليل الحاسم: صلاحية الكتابة قائمة
```
POST /rest/v1/partners  {"name_ar":"ROTATION-VERIFY-PROBE", ...}
→ HTTP 400
  23502: null value in column "owner_id"
  details: Failing row contains
           (0f8b584f-2a31-4544-b027-d1335a438fb9, null, ROTATION-VERIFY-PROBE, ...)
```

هذا **بالضبط نفس السلوك الذي رصدته قبل التدوير المزعوم** — ولم يتغيّر.

الفارق الجوهري: الرد **ليس** رفض مصادقة. الطلب اجتاز المصادقة → اجتاز فحص الصلاحيات → دخل Postgres → **بنى الصف فعلاً** (لاحظ الـ UUID المولَّد والقيم في `Failing row contains`) → وفشل فقط على قيد `owner_id NOT NULL`.

بمعنى مباشر: **لو أُرسل `owner_id` صالح لنجح الإدراج.** المفتاح يملك صلاحية كتابة كاملة على بياناتك المالية.

> تحققت أن الاختبار لم يترك أثراً: `partners` تحتوي **0** صف مطابق لـ `%PROBE%`.

### 4 — `anon` القديم: لا تنخدع بالـ 401
```
REST /transactions   → HTTP 401  {"code":"42501", "hint":"GRANT SELECT ON public.transactions"}
/auth/v1/settings    → HTTP 200
```

الـ 401 هنا **مضلِّل**. الكود `42501` هو خطأ **صلاحيات Postgres** ("امنح الدور الصلاحية")، أي أن المفتاح **قُبل** لكن دور `anon` محروم من الجداول — وهذا نتيجة migration الـ grants، لا نتيجة تدوير.

الدليل القاطع: نفس المفتاح يعطي **HTTP 200** على `/auth/v1/settings` (endpoint مفتوح لا يتطلب صلاحيات جداول). مفتاح مُبطَل لا يعطي 200 في أي مكان.

### 5 — `sbp_` access token
```
GET /v1/projects/nwpyeobuxzbdnnzyfyqw
→ HTTP 200
  {"id":"nwpyeobuxzbdnnzyfyqw", "name":"Terranex",
   "organization_id":"yvomdypgutwalyvforcp", ...}
```
يعمل ويقرأ بيانات المشروع والمؤسسة.

### 6 — الاتصال الحالي سليم ✅
المفتاح الذي أستخدمه (`sbp_` عبر Management API) يعمل ويعيد بيانات صحيحة — لذا **الفشل أعلاه ليس مشكلة اتصال**، بل حقيقة أن المفاتيح القديمة نشطة.

## لماذا توقفت

`service_role` **يتجاوز RLS بالتصميم** — لا سياسة ولا صلاحية تحدّه. إصلاح TRUNCATE الذي طبّقته يحمي من دور `authenticated` فقط، ولا أثر له على `service_role`.

طالما المفتاح مكشوف ونشط:
- أي شخص يملكه يقرأ ويكتب كل البيانات المالية
- يستطيع الكتابة في `financial_audit_logs` أو محوه
- كل الضمانات التي تحققنا منها (RLS، العزل، append-only، حراس الحذف) **لا تنطبق عليه**

تنفيذ البنود المتبقية وإصدار تقرير "كل شيء سليم" الآن سيكون تقريراً مضلِّلاً عن نظام بابه الخلفي مفتوح.

### تدوير JWT (يبطل `anon` و `service_role` معاً)
**Dashboard → Project Settings → API → JWT Settings → Generate new JWT secret**

> ملاحظة: هذا الزر هو ما يُبطل المفاتيح فعلياً. نسخ المفاتيح من الصفحة أو تعديل `.env` **لا يُبطل القديم**.

### إبطال الـ access token
**Dashboard → Account → Access Tokens → Revoke** للـ `sbp_f687…`

### ⚠️ بعد التدوير مباشرة
حدّث `VITE_SUPABASE_PUBLISHABLE_KEY` في Vercel، وإلا سيتوقف التطبيق عن العمل.

### التحقق
```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://nwpyeobuxzbdnnzyfyqw.supabase.co/rest/v1/transactions?select=id&limit=1" \
  -H "apikey: <القديم>" -H "Authorization: Bearer <القديم>"
```

❌ `200` = لم يتم · ❌ `42501` = لم يتم (صلاحيات لا مصادقة)

## اقتراح لتجنّب التعطّل

البنود الأربعة المتبقية **لا يعتمد أيٌّ منها على حالة المفاتيح** — كلها عمل على الريبو والكود المحلي. أستطيع تنفيذها الآن بالتوازي مع تدويرك للمفاتيح، على أن يبقى التقرير النهائي موسوماً بأن الجانب الأمني غير مغلق.

**تذكير بملاحظتي على `generateRequestId()`:** سآخذ بتوجيهك باستخدام **معرّف مسودة من الواجهة** بدل الوقت المقرّب وحده — هذا يمنع الضغط المزدوج دون منع معاملتين متطابقتين مقصودتين (مثل دفعتين نقديتين بنفس المبلغ لنفس المورد).

قل لي: أنتظر التدوير، أم أبدأ بالبنود الأربعة الآن؟
